# V1.0.5.1 Agent 对比任务优化与对话工作区设计

> 状态：已完成 · 版本 `v1.0.5.1`（V1.0.5 的补丁版本，不替代 V1.0.5）· 日期 2026-11-24
> 范围：**A. Agent Orchestrator 对比任务优化**；**B. `/ask` 对话工作区（Conversation Workspace）UI 重构**。
> 明确不做：V1.0.6 的多轮 Agent 逻辑 / Conversation Memory / 历史消息库 / 新 API / 多轮上下文拼接 /
> 新的消息发送流程 / 新的 RAG 或图谱功能。

---

## 1. 背景：跨朝代对比 Bad Case

- 复现问题：「王安石变法和商鞅变法的区别」→ `insufficient（超过最大工具轮次）`。
- 排查结论：**不是证据不足，而是轮次预算与单调用协议不匹配**：
  1. 旧协议每轮只能调用 **1 个工具**，两个实体 ×（定位 → 取详情 → RAG）至少需要 6–7 次工具轮，
     再留 1 轮 final，必然超过 6 轮硬上限；
  2. 图谱事件标题与用户问法不一致（问「王安石变法」，图谱事件标题是 **「熙宁变法」**），
     `search_events` 一次未命中，模型逐轮换词试探，进一步消耗预算；
  3. 最后一轮仍在调用工具、没有机会输出 final，最终被兜底为 `insufficient`。
- 因此「4 → 6 轮」只是必要条件；真正修复需要三件事：**并行只读工具 + 对比任务专项策略 + 轮次耗尽后的有界收尾**。

## 2. Agent 优化

### 2.1 轮次与安全边界（硬上限，不放开）

| 机制 | 取值 | 说明 |
|---|---|---|
| `MAX_ITERATIONS` / `DEFAULT_MAX_STEPS` / `MAX_STEPS_HARD_LIMIT` | **6** | 工具/规划轮硬上限，外部不可配置更高；单实体问题通常 1–2 轮 |
| `MAX_TOOL_CALLS` | **10** | 工具调用总数独立硬上限（批量调用也受此约束） |
| `tool_batch` 单批 | **2–4** 个调用 | 仅允许彼此独立的只读工具；线程池并行执行后**按模型给出的顺序**吸收证据 |
| `MAX_TOOL_BATCH_RESULT_CHARS` | **24000** | 一轮批量结果注入 Prompt 的总字符预算（单条仍 12000） |
| `MAX_FINALIZE_ROUNDS` | **1** | 轮次耗尽后的「只收尾」调用，不允许执行任何工具 |
| `MAX_FINALIZE_RETRIES` | **1** | 收尾轮 JSON 协议错误时允许再要求重发一次合法 final |

- 死循环保护保留：轮次硬上限 + 工具总量硬上限 + 收尾轮禁止工具；收尾轮若仍返回 `tool_call` /
  `tool_batch` 直接安全兜底，不会形成新的循环。
- 证据要求不降低：grounded 仍必须通过 `EvidenceValidator`（evidence 必须是工具真实返回、有事实详情、
  citation 绑定同一实体；RAG evidence 必须是同一 `chunk_id`）。收尾轮 / 校验修复轮只是重写 final，
  不会放行任何未经验证的证据。

### 2.2 内部协议扩展：`action=tool_batch`（不改变外部 API 契约）

- `backend/agent/schemas.py` 新增 `ToolBatchStep`（`calls` 2–4 个 `ToolCall`）。
- `backend/agent/orchestrator.py`：
  - `parse_model_step()` 支持 `tool_batch`；
  - 同一批工具用 `ThreadPoolExecutor` 并行执行，结果按模型顺序回传并 `absorb` 进证据图；
  - 批量结果回传增加总字符预算，防止 4 条大结果把下一轮上下文撑爆；
  - 工具异常 / 参数非法仍走统一失败信封，模型可据此修正。
- 外部契约（`status / answer / evidence / ui_actions / metadata`、`grounded / insufficient / refusal`）
  **完全不变**；`tool_batch` 只是模型与编排器之间的内部动作。

### 2.3 System Prompt：对比任务专项策略

当问题包含「对比 / 区别 / 异同 / 有什么不同 / 比较」且涉及两个及以上实体时，按三阶段优先策略执行
（不是所有任务的固定流程）：

1. **第一轮并行定位**：一个 `tool_batch` 同时查询双方图谱信息；某个名字一次没命中时不要逐轮换词试探，
   下一批改用 `resolve_entity` / `get_person_events` 兜底；
2. **第二轮并行取证**：一个 `tool_batch`（最多 4 个）同时取双方事件详情与双方 RAG 史料
   （`get_event` A/B + `search_historical_text` A/B），query 直接写「实体名 + 背景/措施/影响/局限」；
3. **第三轮生成回答**：综合双方证据直接输出 final，不继续套娃；证据不足如实说明。

同时新增 **claim ↔ evidence ↔ citation 绑定规则**，并明确 RAG claim 必须与同一 `chunk_id` 的
rag evidence 一一对应，避免模型引用 A chunk 却提交 B chunk 证据导致强制降级。

### 2.4 轮次耗尽后的有界收尾与校验修复

- **收尾轮**：6 个工具轮用尽后，追加一次「只收尾」调用（不允许工具），把已获得的工具结果整理成 final；
  若 JSON 非法允许一次协议修复重试；成功解析后仍走原证据校验。`steps` 反映真实模型调用轮次（≤ 6 + 2）。
- **校验修复轮**：final 未通过证据校验（如 claim citation 与 evidence 不同实体）且仍有轮次预算时，
  把校验失败原因回传模型，要求重写 final（不执行新工具）。每次重试仍必须通过原校验，因此不降低证据门槛。
- 这两条把「来不及 final / 选错 citation」与「证据不足」区分开，避免误报 `insufficient`。

### 2.5 工具层：人物名 + 事件词的一次命中

- `backend/agent/tools/events.py` 的 `_search_terms()`：当查询是「已知人物名 + 明确事件词后缀」
  （变法 / 改革 / 新政 / 起义 / 之变 / 之战 / 之乱 / 之役 / 改制）时，把人物名也加入检索词。
  - 例：「王安石变法」→ 词项 `{王安石变法, 王安石}`，一次命中 `beisong-10 熙宁变法`；
  - 只对明确事件词后缀生效，避免把「秦始皇 西红柿」这类问题扩展成大量无关人物事件（实测仍为 0 命中）。
- 只新增检索词，不改变结果排序规则、不降低证据要求。

## 3. 前端：对话工作区（Conversation Workspace）

### 3.1 页面结构（`/ask`）

```
顶部导航（品牌 / 页面名 / 时间轴 / 人物图谱 / 悬浮问答 / 返回首页）
推荐问题 chips（单跳简单事实，一行）
┌───────────────────────────── Conversation Workspace ─────────────────────────────┐
│ chatHeader：CONVERSATION WORKSPACE · 你的历史对话 · N 轮 · 会话已保留 · 多轮布局预览 │
│ transcript（纵向对话时间线，单列/分屏自适应）                                      │
│   用户问题（右对齐）→ AI 回答（左对齐，Markdown 正文 + 状态徽标 + 引用区）          │
│   每轮回答独立：answerMeta（grounded/insufficient/refusal）+ 可核验来源 + 引用列表   │
│ guideRail（史引联动占位）｜ copilotPanel（分屏 iframe，视口高度内独立滚动）          │

└──────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 长回答显示问题：根因与修复

**根因（旧实现）**：

1. 页面壳层 `height: 100dvh; overflow: hidden`，对话列表内部再 `overflow-y: auto` → 形成
   「整页不可滚 + 内层滚动」的嵌套结构，长回答在窄容器里被截断；
2. 对话列使用 `flex: 1 0 auto`（`flex-shrink: 0`）→ 长文本的 max-content 宽度会把对话列/卡片撑出容器，
   表现为文字被右侧裁切或覆盖副驾驶面板；
3. 回答卡片没有固定高度，但父级 flex 高度链与 `overflow: hidden` 组合导致实际可视区域受限；
4. `/ask` 页面的 Markdown 渲染器不支持表格 / 引用 / 代码块，长内容排版不稳定。

**修复**：

- 单一滚动容器：整页由文档滚动承载，`/ask` 不再有内部列表滚动条；
- `conversationBody` / `transcript` / `.agentTurn` 改为 `min-width: 0; flex: 1 1 auto`（允许收缩），
  文字正常换行，不再撑破卡片；
- 底部输入区改为 **在文档流中的 sticky 落位**：不遮挡正文、不压缩正文可用空间，滚到对话末尾即回到卡片底部；
- 副驾驶面板在桌面端固定为视口高度内（`position: sticky` + `height: min(100dvh - 20px, 900px)`），
  iframe 内部独立滚动，避免整页与 iframe 两层滚动条互相干扰；
- 抽出共享 `frontend/components/agent/MarkdownMessage.tsx`：标题（h1–h6）、段落、粗斜体、行内代码、
  列表、引用、代码块、表格（横向滚动容器），`/ask` 与悬浮抽屉复用同一实现。

### 3.3 返回聊天后问题丢失：根因与修复

**根因**：

1. transcript 只保存在 React 内存（`AgentContext`），页面重建 / 刷新 / 从时间轴回到 `/ask` 时状态丢失；
2. 从时间轴「返回聊天」重进 `/ask` 时，上一次回答的史引联动目标会让副驾驶面板自动重新展开，
   窄屏下 `copilotMode` 直接隐藏对话卡片，看起来像「问题没了」；
3. 返回后没有恢复滚动位置，长对话落在页顶。

**修复**：

- `AgentContext` 增加 **sessionStorage 会话持久化**（key `histolink.agent.transcript.v1`）：
  - 首帧统一渲染欢迎语，mount 后再恢复会话 → 不产生 SSR/CSR hydration mismatch；
  - 恢复完成前不写回，避免首帧欢迎语覆盖已保存会话；
  - 损坏 / 版本不符数据安全回落欢迎语；
  - 新增 `isRestored` 供页面等待会话恢复后再做滚动 / 面板决策。
- `/ask` 页面重新进入时**不自动重开旧副驾驶面板**（新回答仍自动展开），落点就是对话列表；
- 页面级滚动位置持久化（`histolink.ask.scroll.v1`）：区分「用户真实滚动」与 Next 路由复位，
  返回聊天 / 路由往返时恢复阅读位置；
- 返回后用户原始问题、AI 回答、引用与状态全部保留，不需要重新提问。

### 3.4 为 V1.0.6 多轮对话预留（只做 UI 结构）

- 对话时间线天然支持「多条用户问题 → 多条 AI 回答」顺序延伸；每条消息独立 key、独立滚动高度；
- 每轮回答独立挂载：正文 Markdown、状态徽标、可核验来源数、引用列表、模型降级提示；
- 底部输入区已固定为工作区结构的一部分，预留输入框 / 发送按钮 / 自动扩展 / Enter 发送 / Shift+Enter 换行；
- 提供 **静态多轮布局预览**：`/ask?preview=multiturn`（4 条静态消息，含表格、代码块、引用、
  「已核验 / 资料不足」两种状态徽标），用于在接入多轮业务前锁定版面；
  预览模式禁用发送并标注「未连接发送与多轮业务逻辑」；
- **未实现**：多轮 Agent、Conversation Memory、历史消息持久化（数据库）、新发送流程、上下文拼接。

### 3.5 响应式与视觉

- 桌面端：单栏 800px 阅读宽度；打开史引副驾驶后 `conversation(≈35%) + panel(≈65%)` 分屏（1360px）；
- ≤ 900px：分屏收窄；≤ 720px：工作区改单列、副驾驶全宽、对话气泡 94%；
- 窄屏实测无横向溢出、无嵌套滚动、无裁切，输入区始终在视口内；
- 视觉沿用史脉既有设计语言（宋体标题、米色纸感、暗红强调、印章 / 史令史引双人格），
  未引入与品牌冲突的装饰卡片。

## 5. 已知限制与 V1.0.6 边界

- 多轮对话仍是**单轮问答 UI 预留**：还不支持真正基于上一轮的连续追问 / 上下文拼接 / 消息持久化；
- 对比回答的「历史局限」等维度取决于 RAG 语料覆盖范围；语料未覆盖时按现有规则如实说明缺失，
  不编造（这是 V1.0.5 的既有产品边界，不是本次回归）；
- 工具层 `search_events` 的「人物名 + 事件词」扩展只覆盖有限事件词后缀；如需更完整的别名 /
  事件同义词表，建议在 V1.0.6 随多轮一起补数据侧别名词典；
- V1.0.5 基线遗留（非本次范围）：`backend/.venv` 与本机 `requirements.txt` 的 RAG 依赖状态
  （chromadb / numpy 版本）由用户 RAG 改造工作流管理，本次未纳入提交；本地 RAG 向量库为
  gitignore 产物，重建命令：
  `backend\.venv\Scripts\python backend\scripts\ingest_rag.py`。
