# V1.0.5.4 · 基于事实的对比分析（二次归纳）设计说明

> 版本背景：V1.0.3 的防幻觉底座要求 **grounded 正文由服务端写死**（模型不能生成任何用户可见文本），
> 因此「商鞅变法与王安石变法的区别」只能罗列双方基础事实、没有对比总结。
> V1.0.5.4 在不破坏底座的前提下增加**受控二次归纳**层：模型只在「已经 grounded 的对比 / 总结类问题」
> 上额外做一次归纳，结果作为**独立可选字段**下发，并必须通过服务端证据链校验。
>
> 相关文件：`backend/agent/{comparison.py,orchestrator.py,prompts.py,validator.py,schemas.py}`、
> `backend/contracts/models.py`、`backend/routers/agent.py`、
> `frontend/{lib/agent-client.ts,app/ask/page.tsx,app/ask/ask.module.css}`。
>
> **2026-11-25 修复补丁**：真实测试暴露了对比意图漏判 / 提前判定 `insufficient` / 新窗口冷启动异常 /
> 证据链误杀四类问题，第 1–10 节的部分细节（触发线索、`insufficient` 门槛、校验口径）已由
> 第 11 节更新；补丁的完整根因、实现与验收证据见
> [`V1.0.5.4-对比分析触发与冷启动修复.md`](V1.0.5.4-对比分析触发与冷启动修复.md)。

## 1. 目标与不变量

| 目标 | 不变量 |
| --- | --- |
| 对比 / 区别 / 异同 / 总结类问题给出「背景、目的、结果」等维度的对比归纳 | 三态语义不变（grounded / insufficient / refusal） |
| 对比分析必须是模型「仅根据本轮事实块」的归纳 | 服务端写死的事实实证正文（`answer.markdown`）不变、不混入模型文本 |
| 分析中的年份 / 人物必须可在本轮工具结果中核对 | 不降低任何证据门槛（`EvidenceValidator` 规则原样保留） |
| 分析校验失败时只丢弃分析 | 不降级为 insufficient（事实实证仍然返回） |
| 普通事实问答不多调模型 | 仅在对比 / 总结类 + grounded 时额外一次模型调用 |

## 2. 两层输出结构

最终回答拆成两层，前端按顺序展示：

1. **📜 史料实证**：沿用 V1.0.5.2 服务端写死格式，按 `[人物关系图]` / `[时间轴·大事记]` 分节，
   内容 100% 来自本轮工具真实返回（`answer.markdown`）。
2. **💡 史令对比分析**：模型基于本轮「纯数据事实块」生成的对比总结，放在回答最后；
   只在对比 / 总结类问题、且服务端校验通过时出现（`answer.comparison_analysis`）。

非对比类问题（例如「赤壁之战发生在哪一年」）不会触发二次归纳，`comparison_analysis` 为 `null`。

## 3. 执行流程（Orchestrator）

```
规划循环（最多 6 个工具轮 + 1 次收尾轮）
  → EvidenceValidator 校验 / 服务端重写事实实证 → grounded?
      ├─ 否（insufficient / refusal / 降级）→ 直接返回（不二次归纳）
      └─ 是 → detect_comparison_intent(question)?
              ├─ 否 → 直接返回（普通事实问答不额外调用模型）
              └─ 是 → build_comparison_facts(本轮真实工具结果)
                      → Qwen 二次归纳（JSON 模式、关闭思考、temperature=0、max_tokens=1024）
                      → parse_comparison_analysis（必须 {"analysis": "..."}）
                      → validate_comparison_analysis（年份 / 人物白名单）
                           ├─ 通过 → FinalAnswer.comparison_analysis = 分析文本（正文不变）
                           └─ 不通过 / 模型异常 / 协议错误 → 丢弃分析，只保留事实实证
```

二次归纳调用会合并 token usage；它不计入规划轮次（`steps` 仍表示主循环轮次），
也不会触发任何工具或 UI 动作。

## 4. 触发条件

- **问题线索**（`validator.detect_comparison_intent`，确定性关键词）：
  `对比 / 区别 / 异同 / 比较 / 有什么不同 / 异同点 / 有何不同 / 总结 / 归纳`；
- **回答状态**：主回答为 `grounded` 且未降级（insufficient / refusal 不触发）；
- **证据前提**：本轮通过校验的 evidence 能整理出非空事实块。

触发判定与 `detect_question_focus()` 分开维护：后者决定双源覆盖校验与分节顺序，
前者只是二次归纳开关，两者互不影响，避免「总结类问题」被当成对比类而绕过双源覆盖硬校验。

## 5. 事实块（`build_comparison_facts`）

事实块由服务端从本轮工具真实返回整理，**不含模型文本**：

- 事件：标题、朝代、年份、描述（缺失时回退事件引用摘要）、参与者（正名 + 括号别名）、史料出处；
- 人物：姓名、消歧说明、主要朝代、活动年代、别名；
- 关系：关系两端、关系定性、描述、来源；
- RAG 史料：出处、对应事件、正史 / 传说、年份区间、正文（截断）；
- 整体字符上限 `MAX_FACT_BLOCK_CHARS = 8000`（超长截断，避免撑爆上下文）。

事实块同时产出两个白名单：

- `years`：结构化年份（事件年 / 人物首末年 / RAG 年份区间）+ 事实块文本中出现的
  「显式年份 / ≥3 位裸年份」；
- `person_names`：事实块显式人物 + 事实块文本中出现的已知人物名（含别名；别名是同一人物的不同称呼）。

## 6. 证据链校验（`validate_comparison_analysis`）

任一项失败 → **整段分析丢弃**，只保留事实实证；不降级为 insufficient。

### 6.1 年份校验

- 抽取分析文本中的年份表达式：`公元前 356 年` / `前 350 年` / `公元 220 年` / `1069 年`；
- 带「公元前 / 前 / 公元」前缀的**显式年份**必须命中事实块年份集合；
- 无前缀裸年份：只有 ≥3 位数字（如 `1069年`）才强制校验；1–2 位（如「推行了 20 年」）
  视为「时长」等歧义写法忽略，避免误杀；
- 事实块年份集合只吸收显式年份与 ≥3 位裸年份，避免把事件描述里的时长写进白名单。

### 6.2 人物校验（白名单正向校验）

- 不做「姓 + 名」正则猜人名（避免「开启」命中人物「启」这类误杀）；
- 用快照的**已知人名词典**（`SnapshotStore.persons_by_name`：1,066 位人物正名 + 70 条别名）
  扫描分析文本，命中的每个已知人名必须属于事实块人物白名单；
- 单字姓名不做扫描（宁漏不误杀，见上文）；
- 若命中的名字是白名单某个更长姓名的子串（「李广」vs「李广利」），视为已被覆盖；
- 事实块人物白名单包含人物别名（如「赵顼（宋神宗）」），避免同一人物不同称呼被误杀；
- 已知人名词典之外、且事实块文本里也没有出现过的极生僻姓名无法被识别
  （按「宁漏不误杀」取舍；已收录人物覆盖 1,066 位正名 + 70 条别名）。

### 6.3 其他

- 空文本 / 清理后为空 → 丢弃；
- 超长（>1500 字，与契约 `max_length` 对齐）→ 丢弃；
- 越狱指令标记（「忽略系统提示词」等）→ 先中和再校验；
- 输出必须是唯一 JSON 对象 `{"analysis": "..."}`（容忍整体被 ```json fence 包裹），
  否则视为协议错误并丢弃。

## 7. API 契约（向后兼容）

- 新增可选字段 `Answer.comparison_analysis: ComparisonAnalysis | null`；
- `ComparisonAnalysis.text`：长度 1–1500、已通过服务端校验的分析正文；
- 只有 `grounded` 回答允许携带该字段（Pydantic 校验器强制；其它模式携带即拒绝）；
- **不改任何必填字段**、不改三态语义、`SCHEMA_VERSION` 仍为 `1.0`；
- OpenAPI / 前端 `api-types.ts` 由脚本重新生成；
- 非对比类回答序列化时为 `null`，旧前端忽略未知字段也不会破坏渲染。

## 8. 前端展示

- `answerViewFromEnvelope()` 归一化 `answer.comparison_analysis`（异常结构 / 空文本回退 `null`）；
- `/ask` 回答卡片在「事实实证正文 + 状态徽标 + 引用列表」之后渲染独立卡片：
  `💡 史令对比分析`（暖金描边、独立背景、脚注「事实与引用以上方史料实证为准」）；
- 非对比类问题 / 校验失败时后端不返回该字段 → 卡片整块不渲染；
- 前端只展示服务端文本，不做任何拼接或改写。

## 9. 失败处理矩阵

| 场景 | 行为 |
| --- | --- |
| 二次归纳模型超时 / 429 / 上游错误 | 捕获异常，丢弃分析；主回答仍 grounded（不 500） |
| 二次归纳返回非 JSON / 缺 `analysis` 字段 | 丢弃分析；主回答仍 grounded |
| 分析含未证实年份 | 丢弃整段分析；事实实证保留 |
| 分析含事实块外人物 | 丢弃整段分析；事实实证保留 |
| 分析为空 / 超长 | 丢弃整段分析；事实实证保留 |
| 非对比 / 总结类问题 | 不调用二次归纳 |
| 主回答 insufficient / refusal / 降级 | 不调用二次归纳 |

### 10.2 真实模型冒烟（2026-11-25，Qwen/Qwen3.5-35B-A3B）

**问题 A：「商鞅变法与王安石变法的区别」**（HTTP `POST /api/agent/ask`，经 Next 同源代理）

- `answer.mode = grounded`，`downgraded = false`，**5 次模型调用**（4 轮规划 + 1 次二次归纳），
  7 条引用，`trace.sources` 双源命中；
- `answer.markdown` 为服务端双源事实实证（`[时间轴·大事记]` + `[人物关系图]`），不含分析文本；
- `answer.comparison_analysis.text` 为「背景 / 目的 / 结果 / 影响」四维对比（约 400 字），示例：

  > **背景**：商鞅变法发生于战国时期前359年，由秦孝公主导……熙宁变法发生于北宋1069年，由宋神宗赵顼主导……
  > **目的**：商鞅变法旨在「内务耕稼，外劝战死之赏罚」……熙宁变法推行青苗、免役、均输、市易、保甲诸法……
  > **结果**：…… **影响**：……

- 分析中的年份（前359年 / 1069年）与人物（商鞅、秦孝公、甘龙、杜挚、王安石、宋神宗赵顼）
  全部命中事实块白名单，通过服务端证据链校验后下发；
- 多次复跑（含 HTTP 全链路）未出现 500；个别轮次模型写入了材料外的年份 / 人物，
  按设计整段丢弃分析、只保留事实实证（服务端日志见「二次归纳未通过证据链校验」）。

**问题 B：「赤壁之战发生在哪一年？」**

- `answer.mode = grounded`，**3 次模型调用**（无二次归纳）；
- `answer.comparison_analysis = null`，正文仍为双源事实实证。

## 11. 修复补丁：触发覆盖 / 对比兜底 / 冷启动 / 校验兜底（2026-11-25 追加）

> 完整说明、根因与验收证据：[`V1.0.5.4-对比分析触发与冷启动修复.md`](V1.0.5.4-对比分析触发与冷启动修复.md)。

| 问题 | 修复后行为 |
| --- | --- |
| 隐式对比问法（`…一样吗` / `谁的影响更大` / `相比如何` / `差异`）不触发二次归纳 | `detect_comparison_intent` 扩展为「显式关键词 + 隐式句式」，并与 `detect_question_focus` 共用判定 |
| 模型自述 `insufficient` / 证据校验降级时，在二次归纳前直接返回资料不足 | 新增**对比兜底**：只要本轮图谱里找到 A/B 双方实体，服务端用真实事实重写 grounded 正文并立即二次归纳；二次归纳失败仍保留事实实证 |
| A/B 图谱实体都没查到却被兜底强行 grounded | 兜底只在双方实体都命中时接管；只有一侧 / 都没有 → 保持 `insufficient` |
| 分析提到图谱已有的人物 / 年份被误杀 | 人物放行名单并入「本轮图谱实体人物名 / 别名」；年份允许「公元前221年 ↔ 221年」纪年前缀模糊匹配 |
| 工具结果消息 >20000 字导致 HTTP 503（冷启动偶发异常报错） | 工具结果预算 10000 / 16000 / 18000 三级约束 + Orchestrator 非 system 消息 19000 字安全裁剪 |
| 新窗口恢复旧版 answer 缺字段导致空指针 | 前端 `normalizeRestoredAnswerView()` 归一化恢复、`session_id` mount 初始化、`model_id` 冷启动策略 |
