# 项目现状与开发前置审核报告（V1.0 Agent）

> 审查对象：HistoLink 仓库当前工作区（HEAD `b1ef8f2`，含 V0.9.0 未提交改动）
> 审查日期：2026-11-23
> 修订：v1.1（2026-11-23）——纳入 Q1–Q6 产品决策，见 §0.5 与 §8
> 审查性质：技术架构审查（只读代码 + 数据实测，不含任何实现代码）
> 审查范围：前端路由 / 时间轴与图谱组件 / 数据层 / FastAPI 后端 / SPEC·README·CHANGELOG 规划
> 实测方式：用仓库自带 TypeScript 数据模块做只读统计（671 条时间轴事件、34 条图谱补足事件、639 对关系、18 期为细览 + 7 组简阅共 25 张图）

## 0. 结论摘要

### 0.1 一句话结论

**方案方向成立，但当前仓库不具备直接开工 V1.0.1 的四个前提**：后端没有可查询的数据、人物没有稳定 ID、UI 状态不能被外部驱动、引用信息没有结构化。建议先补一个「V1.0.0 前置改造」，再按调整后的 7 版推进。

### 0.2 四项审查结论

| # | 审查项 | 结论 | 一句话依据 |
|---|---|---|---|
| 1 | 前端路由 / 组件状态 / 数据结构盘点 | **完成**（见 §2） | 3 个路由；时间轴与图谱状态全部是页面内 `useState`；后端只有 `GET /api/health` |
| 2 | 人物 / 事件 ID 能否支撑 Agent 精准调用 | **不通过**（事件 ID 可用，人物 ID 不可用） | 人物节点 `id = 姓名`（`person-graph.ts:191`），1059 个姓名被当作主键，且已存在同名异人 |
| 3 | 七个小版本顺序 | **有条件通过**，需调整 4 处 | 缺「数据服务层」；RAG 语料实际不存在；Action 契约必须在 .1 冻结；记忆字段应进首版契约 |
| 4 | API 如何驱动 UI Action | **建议采用「服务端语义动作 + 客户端解析视图」** | 现有视图规则（184/188 分界、简阅只显示 `importance=3`、分期映射）都在前端，后端不应重复实现 |

### 0.3 五个 P0 阻塞项

| 级别 | 问题 | 证据 | 影响 |
|---|---|---|---|
| P0-1 | 后端无数据服务 | `backend/main.py` 全文 66 行，仅 `GET /api/health`（`:64-66`）；所有数据在前端 TS 模块 | V1.0.2 工具层无数据可查，"Agent 调用历史知识工具"无从落地 |
| P0-2 | 人物 ID = 姓名 | `person-graph.ts:187-199` 节点 `id: name`；`EVENT_PARTICIPANTS` 值是 `string[]`；关系数据 `a/b` 也是姓名 | 无法精准实体链接；同名异人串数据；SPEC §4.5 的 `person_id` 方案零实现 |
| P0-3 | UI 状态不可外部驱动 / 不可深链接 | `timeline/page.tsx:195-199`、`graph/page.tsx:36-45` 全部本地 state；全仓库无 `useSearchParams` / `router.push` | UI Action 无处落地；SPEC §3.2 要求的深链接与刷新恢复也未实现 |
| P0-4 | 引用信息未结构化 | `TimelineEvent` 无 `sourceRefs` 字段，出处只以「（据《…》）」写在 `description` 文本里 | 无法生成可核验引用；V1.0.5 的 RAG 校验器（SPEC §8.7）没有输入 |
| P0-5 | 参与者语义未定义 | `participants` 既表示"参与"，也混入"提及/思想对立"（如 `ming-07` 阳明心学含朱熹；关系库有「王阳明×朱熹 思想对立」） | 工具回答"谁参与了 X"会给出错误事实；关系图语义与史实语义不等价 |

### 0.4 审查结论一句话版

- **可以保留**：事件 ID、时间轴/图谱数据与组件、V0.9.0 的 `/api` 同源代理与 CORS 方案。
- **必须先补**：数据快照导出 + 后端只读数据服务、人物主数据与 `person_id`、API/Action 契约冻结、引用结构化。
- **建议调整**：7 版顺序（见 §4.4），把「契约 + 数据 + 评测」全部前移到 V1.0.1。

### 0.5 已确认的产品决策（2026-11-23）

| # | 决策 | 对架构的直接影响 |
|---|---|---|
| Q1 | **全局悬浮抽屉 + `/ask` 独立页**；浏览时用抽屉，跨页用深链接 | V1.0.1 需要 `AppShell` 骨架（`layout` 级 Agent 容器 + `/ask` 路由占位）；两个入口必须共享同一份会话状态，不能各存一份 |
| Q2 | **同页自动，跨页需用户点击按钮确认** | Action 信封增加 `surface/target` 语义；`auto` 只作建议值，由前端按"目标页 == 当前页"强制判定；跨页动作一律渲染为确认按钮 |
| Q3 | **V1.0 只做「事件摘要 + 关系简述 + 引据书目」的 BM25 检索**，不引入外部维基全文 | V1.0.5 范围收敛：无外部语料、无向量库；引用单元 = 事件/关系记录；`sourceRefs` 与"可引用文本"必须在 .1 结构化 |
| Q4 | **坚决不允许推测性回答**，无资料必须说「资料不足」 | `answer.mode` 增加 `grounded / insufficient / refusal` 三态；生成前强制基于工具结果，生成后过校验器，无依据直接走固定拒答模板 |
| Q5 | **有上下文自动选，无上下文必须弹候选列表** | API 增加 `clarification` 分支与候选实体结构；工具 `resolve_entity` 返回候选；前端增加候选选择 UI；禁止"默认取第一条" |
| Q6 | **个人开源学习项目，非商用**；沿用 shiji-kb 的 CC BY-NC-SA | 引用/页脚/API `attribution` 保留署名与非商业声明；发布门禁加入许可检查；商用需先替换 shiji-kb 派生数据 |

> 这 6 条决策已经写入 §4.4 的版本路线、§5 的 API/UI Action 契约、§5.7 的降级矩阵与 §8 的落地清单。除非重新决策，V1.0 的实现与验收以本节为准。

> 关于 Q2 的一处措辞：你举例的「时间轴点图谱」若指 `/timeline` → `/graph` 的路由跳转，按本报告的机械规则属于**跨页**（应走确认按钮）；只有动作目标与当前路由相同才自动执行。若你希望这种跳转也自动，需要在 V1.0.4 引入"同页双面板/预览"，见 §8.2 E7。默认按跨页确认处理。

## 2. 现状盘点

### 2.1 运行形态与代码规模

| 层 | 现状 | 规模 |
|---|---|---|
| 前端 | Next.js 16 App Router + React 19 + TS 5.9，CSS Modules，无 UI 框架、无状态管理库 | 3 个路由、3 个组件、5 个数据模块 |
| 后端 | FastAPI + Uvicorn，单文件；仅健康检查 | `main.py` 66 行 |
| 数据 | 全部为前端 TS 常量，随前端打包；无数据库、无 JSON 快照、无 API | `timeline-events.ts` 223KB、`person-relations.ts` 167KB、`person-graph.ts` 30KB |
| 部署 | `next.config.ts` 把 `/api/*` 同源代理到 `127.0.0.1:8000` | 浏览器不直连后端 |

**关键事实：后端当前不持有任何业务数据。** `backend/requirements.txt` 只有 `fastapi`、`uvicorn`，没有 ORM、没有 HTTP 客户端、没有检索库、没有 LLM SDK。V1.0.1 说的"基础设施"如果只理解为 FastAPI 脚手架，会直接导致 V1.0.2 无数据可用。

### 2.2 前端路由与内部状态

| 路由 | 文件 | 页面内状态 | URL 可恢复 | 外部可驱动 |
|---|---|---|---|---|
| `/` | `app/page.tsx` | `health`、`toast` | 否 | 否 |
| `/timeline` | `app/timeline/page.tsx` | `mode`（简阅/细览）、`dynasty`、`groupId`、`selectedId`、`showEgg` + `lastDynastyByGroup`（`useRef`） | 否 | 否 |
| `/graph` | `app/graph/page.tsx` | `mode`、`eraId`、`scopeId`、`centerPersonId`、`searchQuery`、`isSearchOpen`、`activeSearchIndex` + `lastDetailEraByScope`（`useRef`） | 否 | 否 |
| `/ask` | **不存在** | — | — | — |

要点：

1. **没有任何路由参数（`?event=`、`?center=`、`?era=`）**。SPEC §3.2 要求"所有路由参数必须可深链接、可浏览器前进后退；刷新后状态可从 URL 恢复"，目前完全未实现。这既是既有缺口，也是 V1.0.4 的硬前置。
2. **状态分散在两个页面**，没有全局 store（`package.json` 无 Zustand）。SPEC §9 设想的 `ui / entities / graph / timeline / qa` 分片不存在。
3. **页面状态与组件状态是分离的**：时间轴事件卡片由 `selectedId` 派生（`timeline/page.tsx:230`），图谱关系面板的"选中关系"却藏在 `PersonGraph2D` 内部（`PersonGraph2D.tsx:97`），外部无法设置。这决定了 UI Action 能做什么、不能做什么。
4. **模式切换有记忆逻辑**：`lastDynastyByGroup`、`lastDetailEraByScope` 是页面私有 ref。外部若要"跳到某事件"，必须按同样规则推导 mode/dynasty，不能只设 `selectedId`。

### 2.3 时间轴数据结构与渲染管线

```
timeline-events.ts: TIMELINE_EVENT_RECORDS（无 participants）
        + timeline-participants.ts: EVENT_PARTICIPANTS[id] = string[]
        → TIMELINE_EVENTS（合并 participants，:5786-5789）
        → timeline/page.tsx: filter（按 dynasty 或 group + importance=3）
        → buildLayout()（:133-185）：按天文纪年线性映射 + 贪心错层
        → 圆点渲染 + 点击 setSelectedId
        → 卡片：positioned.find(id === selectedId)（:230）
```

关键约束（Agent 必须知道，否则会"高亮不到"）：

| 约束 | 现状 | 对 Agent 的影响 |
|---|---|---|
| 一次只渲染一个朝代（细览）或一个大断代（简阅） | `timeline/page.tsx:209-216` | 目标事件不在当前朝代时，必须先切朝代，否则 `selected` 为 `null`，点击动作静默失效 |
| 简阅模式只渲染 `importance === 3` | 同上 + `importanceOf` | 目标事件是 1/2 级时，必须先切"细览" |
| 卡片只在 `positioned` 内查找 | `:230` | 同上，动作需要"设置 mode+dynasty+event"三元组，不能只给 eventId |
| 无"高亮一组事件/区间"能力 | 只有单 `selectedId` | "高亮时间轴一段范围"需要新增组件能力，不能假装能联动 |
| 彩蛋事件 `isSpecial` 混在数据里 | `special-star-1893`，无参与者 | Agent 工具必须默认排除，否则会被当成史实回答 |

### 2.4 图谱数据结构与组件

```
TIMELINE_EVENTS + WEIJIN_EVENTS
  → buildPersonGraph(events, dynasties)（person-graph.ts:130-202）
      每个事件参与者两两成边；weight = 共同事件数
      node.id = 姓名（:191）
      edge.id = `${A}__${B}`（排序后）
      edge.relation = PERSON_RELATION_INDEX.get(pairKey)
  → 18 期 ERA_GRAPHS + 7 组 PERSON_GRAPH_SCOPES
  → /graph 页面按 mode 取 active.graph
  → PersonGraph2D：只取 center 的一度邻居（:56-74）
```

关键约束：

| 约束 | 现状 | 对 Agent 的影响 |
|---|---|---|
| 节点 ID = 姓名 | `person-graph.ts:191` | 见 §3.2，是本次审查最严重的问题 |
| 一次只显示中心人物的 **1 跳**邻居 | `PersonGraph2D.tsx:56-74` | "聚焦图谱两人关系"只能以 A 为中心再看 A–B 边；无法展示两点间路径 |
| 关系选中态在组件内部 | `PersonGraph2D.tsx:97`，且 `centerPersonId` 变化时重置（`:101-103`） | 外部无法"打开某两人的关系面板"；需新增受控 prop |
| 无高亮/聚焦 API | props 仅 `data / centerPersonId / onCenterPersonChange`（`:50-54`） | "高亮节点/边"是新增能力；V1.0.4 需先改组件接口 |

### 2.5 后端现状

`backend/main.py` 只有一件事：CORS 配置 + `GET /api/health`（`:64-66`），返回 `{"ok": true, "version": "0.9.0"}`。没有 Pydantic 模型、没有路由分组、没有数据加载、没有 OpenAPI 版本策略、没有错误 envelope、没有 LLM 客户端。

已有可取之处：V0.9.0 的 **同源 `/api` 代理**（`next.config.ts:64-73`）与**可配置 CORS**（`main.py`）方案是正确的，V1.0 应沿用，不要另起炉灶。

## 3. 审查重点二：ID 体系能否支撑 Agent 精准调用

### 3.1 事件 ID：可用，但需要"冻结 + 契约测试"

现状（实测）：

| 指标 | 值 |
|---|---|
| 事件总数（含图谱补足） | 705（671 + 34） |
| 数字序号型 ID | 548（如 `qin-01`、`tang-37`、`chunqiu-01`） |
| 语义 slug 型 ID | 157（如 `qin-unify`、`handong-dongzhuo`、`weijin-zhulin`） |
| 数字序号连续性 | 22 个数字序号前缀全部连续，无空洞、无重复 |
| 非法年份 | 0 条 |
| `id` 唯一性 | 校验脚本已覆盖（`validate-data.mjs:88-92`） |

**优点**：现有事件 ID 唯一、稳定、已写入 README 约定"只增不改"，并已被 25 张图谱的事件白名单硬引用（`XIJIN_EVENT_IDS` 等）。可以直接作为 Agent 工具的外部键。

**风险**：

1. **双轨命名**：数字序号（位置型）与语义 slug（内容型）并存。位置型 ID 的稳定性依赖"只在末尾追加"的纪律，一旦有人插入或重排，ID 语义就漂移；而现有文档只在 README 口头约定，没有机器可执行的锁。
2. **无 ID 契约**：没有正则、没有前缀注册表、没有"ID 清单快照"。Agent 生成的 action 若引用不存在的 ID，前端无法区分"模型幻觉"与"版本不一致"。
3. **两类事件可见性不同**：`weijin-events.ts` 的 34 条只进图谱、不进时间轴（README §10）。Agent 回答"有哪些事件"时若混用，会出现"答得出但时间轴找不到"。
4. **彩蛋事件混入主数据**：`special-star-1893`（`isSpecial: true`、无参与者、1893 年）。工具层必须默认排除，否则会被当成史实。

**建议**：

- 保留现有 ID，**不重编号**。
- 新增 `event-ids.lock.json`（由导出脚本生成：id → title/dynasty/year/hash），CI 比对：已有 ID 的元信息变了要显式写 changelog，ID 消失直接失败。
- 新增 ID 统一用语义 slug（`<dynasty>-<event-slug>`），数字序号型仅冻结存量。
- 快照里为每个事件加 `surface: ["timeline","graph"]`、`isSpecial`、`importance`、`personIds`，让工具层不必自己判断。

### 3.2 人物 ID：**这是本次审查最严重的架构缺口**

**事实**：

- `PersonGraphNode.id` 直接等于 `name`（`person-graph.ts:187-199`）。
- `EVENT_PARTICIPANTS` 的值是 `readonly string[]`（`timeline-participants.ts`），关系库 `PersonRelationRecord.a/b` 也是姓名，边 ID 是 `姓名__姓名`（`person-relations.ts:53-55`）。
- 全仓库没有人物实体表：没有生卒、身份、时期、别名以外的唯一键。

**实测证据（同名异人已经存在）**：

| 姓名 | 出现事件 | 判定 |
|---|---|---|
| `梁太后` | `handong-zhidi`（146，东汉）／`beisong-25`、`beisong-26`、`xixia-09`（1081–1082，西夏） | **两个人**（东汉梁太后 vs 西夏梁太后），却共用一个"主键"；在 `qinhan`、`beisong`、`xixia` 三张图中都是同一 ID |
| `刘崇` | `xihan-wangmang-regent`（6，西汉，安众侯刘崇）／`wudai-17`（954，北汉刘崇） | **两个人**，相差 948 年 |
| `朱熹` | `nansong-17`、`nansong-18`（1175/1195）／`ming-07`（1527，阳明心学） | 后一条是"被提及"，不是参与者；参与者字段语义已漂移 |

另有多处跨期复用：139/1022 个图谱节点出现在不止一个细览期（如 `完颜阿骨打` 出现在北宋/辽/西夏/金四期），这对"同一个人在不同图里"是合理的，但**只靠姓名无法区分"同一人的跨期出现"与"同名异人的错误合并"**。

**由此产生的连锁问题**：

1. **Agent 实体链接无法做**：用户问"梁太后"，系统无法知道问的是哪一位；问"李密"时 SPEC §12-B 要求的两条独立记录根本不存在（数据里只有隋末李密）。
2. **工具结果不可信**：`get_person_events("梁太后")` 会同时返回 146 年与 1081 年的事件。
3. **UI 精准聚焦不可做**：`graph.focus_person` 只给姓名，前端无法决定该开哪一期图。
4. **关系数据不可迁移**：关系库以姓名为键，未来拆出 `person_id` 时，`a/b`、`pairKey`、边 ID、名人堂、别名表全都要迁移。
5. **SPEC 验收 B 组（重名）无法通过**：B1 要求"李密（西晋）与李密（隋末）两条记录"，当前数据与模型都不具备。

**建议：分两步走，V1.0 用"最小可用实体层"，V1.1 再统一前端口径。**

**第一步（V1.0.1，必须做）——新增全局人物主数据，不动现有渲染：**

- 新增 `frontend/data/persons.ts`（或由构建脚本生成的 `persons.json`），字段：
  `id / displayName / disambiguator{period, role} / aliases[] / dynasty / eventIds[] / firstYear / lastYear / status`。
- ID 规则：`p-<dynasty-code>-<name-slug>-<2位序号>`，如 `p-han-liangtaihou-01`、`p-xixia-liangtaihou-01`。**不得只由姓名派生**，避免改名/同名冲突。
- 生成方式：从 `EVENT_PARTICIPANTS` 反向聚合，按"姓名 + 朝代聚类"给默认 ID；对已知歧义（梁太后、刘崇、朱熹）人工拆分并在 `persons` 里显式登记；导出"同名报告"供人工裁决。
- 兼容策略：**时间轴/图谱渲染仍可用姓名**（单张图内姓名唯一，校验已保证），Agent 工具与 API 一律用 `person_id`；快照里同时提供 `person_id → 姓名 + 期` 与 `姓名 + era → person_id` 两个索引。UI Action 对歧义人名强制带 `era_id`（见 §5.4）。
- 补 `disambiguator`：至少覆盖所有重名与高频人物（如「梁太后（东汉·梁冀妹）」/「梁太后（西夏·毅宗后）」）。

**第二步（V1.1，可选）**——把 `participants` 全面替换为 `personIds`，图节点/边/关系库改用 `person_id` 作为键，届时再做关系库迁移。

> 注意：不要在 V1.0.1 直接重写 4000 行关系库的 `a/b`。那是数据迁移，不是 Agent 前置；现有"单图内姓名唯一"的校验（`validate-data.mjs:150`）足以支撑 V1.0 的展示层。

### 3.3 关系边 ID 与关系语义

- 边 ID = `pairKey` = 姓名排序后 `__` 连接（`person-relations.ts:53-55`），本质上仍是"姓名对"；V1.0 可作为临时键，但快照里应同时给 `person_id_a/b`。
- **关系语义要与"共事"区分**：`PERSON_RELATIONS` 里存在「王阳明 × 朱熹：思想对立」这种跨 300 年的"关系"，它同时被 `ming-07` 的参与者列表"合法化"为一条边。Agent 回答"王阳明和朱熹是什么关系"时若只返回"共同参与 1 件事件"会误导。建议关系记录增加 `nature` 枚举：`interaction`（真实互动）/ `lineage`（师承、思想）/ `evaluation`（评价、对立）/ `kinship`，工具输出时一并返回。

### 3.4 ID 体系审查结论

| 对象 | 当前是否可支撑 Agent | 结论 |
|---|---|---|
| 事件 | **可以** | 冻结 + 加锁文件 + 契约测试即可 |
| 人物 | **不可以** | 必须新增 `person_id` 主数据与消歧；这是 V1.0.1 的硬前置 |
| 关系边 | **暂时可以** | V1.0 用姓名对，快照里补 `person_id` 映射；V1.1 再迁移 |
| 分期（era/scope） | 可以 | ID 已稳定；需把"人属于哪些期"预计算进快照，供 Agent 解析目标图 |

**验收样例（建议写进 V1.0.1 的 DoD）**：

1. 输入"梁太后"，工具返回 2 个候选（东汉 / 西夏），各带 `disambiguator` 与 `era_ids`；
2. 输入"梁太后 + 西夏"，只返回西夏那一位的事件；
3. 输入"朱熹"，`get_person_events` 不返回 `ming-07`（除非显式查"提及"）；
4. 输入任意 `person_id`，都能反解出 `displayName` 与所在图（epoch）列表；
5. 所有返回 ID 都能在快照里查到（0 悬空）。

## 4. 审查重点三：七个小版本顺序评审

### 4.1 总体判断

**方向正确，顺序需要调整。**

正确之处：

- "先基础设施 → 工具 → 规划器 → UI → RAG → 记忆 → 质量"符合依赖方向；
- 把结构化工具放在 RAG 之前是**对的**——本项目最大的资产是 671 条结构化事件与 639 对关系，先用好它，再谈语义检索；
- "Agent 只读、不改正式数据"与现有"数据层加法、不改渲染"的工程纪律一致。

需要调整之处（4 处）：

1. **V1.0.1 缺"数据服务化"**：后端没有数据、没有快照导出，V1.0.2 无法开工。
2. **V1.0.1 必须冻结 API / Action / Tool 三份契约**：否则 V1.0.3 的输出格式会在 V1.0.4 被推翻，V1.0.6 加记忆又要改协议。
3. **V1.0.1 必须做人物主数据**：ID 是工具层与 UI 层共同的地基，放到 V1.0.2 做会导致 V1.0.2/3/4 全部返工。

### 4.3 三处"因果倒置"的详细说明

**（1）工具层不能先于数据服务层。**
V1.0.2 的工具本质是"对结构化数据做查询"。当前数据只存在于前端打包产物里，后端进程读不到。选项有三种：

- A. 后端 import 前端 TS：不可行（Python 读不了 TS，且会绑定前端构建）。
- B. 后端直连前端打包后的 JS：脆弱，不可取。
- C. **构建期导出 JSON 快照，后端启动加载**：推荐。数据量级（约 1–2MB JSON）完全不需要数据库。

因此 V1.0.1 必须包含 `scripts/export-snapshot.mjs` 与 `backend/data/snapshot.v1.json`，这是工具层的唯一数据源。

**（2）Action 协议不能晚于规划器。**
规划器（1.0.3）的输出形状就是"回答 + 动作"。如果 1.0.1 不定协议，1.0.3 会先按自己的想象写出 `answer` 结构，1.0.4 再改，1.0.6 再改一次。**契约先行**是这类"模型输出驱动 UI"项目的铁律。

**（3）RAG 的"引用"必须早于 RAG 的"检索"。**
引用不是 RAG 的附属品，而是数据模型的属性：哪个事件对应哪部史书的哪一段。当前 `TimelineEvent` 只有一段 `description`，出处写死在正文括注里。V1.0.1 就应该把 `sourceRefs` 结构化（可先正则抽取 + 人工抽查），否则 V1.0.5 的引用校验器（SPEC §8.7 V1–V7）没有可校验对象。

## 5. 审查重点四：API 设计——让 FastAPI 数据直接驱动 UI Action

### 5.1 五条设计原则

1. **契约先行**：先冻结 JSON Schema（请求 / 回答 / 动作 / 工具 / 快照），前后端共享生成的 TS 类型（FastAPI OpenAPI → `openapi-typescript`）。不要在实现里"边写边定"。
2. **服务端只给"语义 + ID"，客户端解析"视图状态"**：后端说"把事件 `qin-unify` 放到时间轴"，前端自己决定要不要切细览、切哪个朝代。理由见 §5.5。
3. **动作必须由服务端从工具结果确定性构造，绝不让模型直接输出 action JSON**。模型可以选工具、选实体（从候选列表），但最终 `ui_actions` 由服务端用**已校验的 ID** 生成。这样"模型幻觉 ID"最多导致工具无结果，不会导致前端乱跳。
4. **只读白名单**：V1.0 的 API 不允许任何写库/改数据的端点；动作类型是有限枚举，前端只执行已知类型，未知类型静默忽略并上报。
5. **版本化 + 快照号**：每个响应带 `schema_version` 与 `snapshot_version/hash`；前端若发现快照不一致，降级为"仅文字回答，不执行动作"并提示刷新。
6. **歧义显式化（Q5）**：实体解析有上下文则自动收敛到唯一候选；无上下文必须返回候选列表让用户选择，禁止静默取第一条；澄清请求不是"回答"，不进入生成环节。

### 5.2 建议的接口清单

| 方法 | 路径 | 用途 | V1.0 |
|---|---|---|---|
| GET | `/api/health` | 保留现状 | 已有 |
| GET | `/api/meta` | 返回 `api_version / schema_version / snapshot{version,hash,counts} / capabilities[]` | .1 |

> 候选顺序由服务端按"上下文匹配 → 同名组内知名度"排序；前端**禁止默认选中第一条**。用户选择后，客户端带 `clarification_id` + 选中的 `person_id` 重新请求（无状态实现，服务端不必缓存澄清会话）。

`answer.mode` 取值（Q4）：`grounded`（有工具依据）/ `insufficient`（资料不足，固定文案 + 相关条目，不进入生成）/ `refusal`（超范围，固定拒答）。

流式（`.4`）建议事件序列：`meta` → `delta`（多段）→ `citation` → `ui_action` → `done`（携带完整对象）。前端**在 `done` 之前不执行动作**，避免"动作先到、回答后到"的错位。

### 5.4 UI Action 动作清单（按现有能力分级）

| 动作类型 | payload | 现有能力 | 需要改造 | 建议版本 |
|---|---|---|---|---|
| `timeline.focus_event` | `event_id` | 可通过 state 设 `selectedId` | URL 化；动作需自动推导 mode/dynasty | .4 |
| `timeline.focus_dynasty` | `dynasty` / `group_id` + `mode` | 可 | URL 化 | .4 |
| `timeline.highlight_events` | `event_ids[]` | **无**（只有单选） | 新增高亮集合 + 可能需"高亮区间" | .4（可延后） |
| `graph.focus_person` | `person_id` + `era_id`（歧义时必填） | 可设 `centerPersonId` | 需"person_id → era"索引；URL 化 | .4 |
| `graph.focus_relation` | `person_id_a` + `person_id_b` | **无**（选中关系是组件内部 state） | `PersonGraph2D` 增加受控 `selectedPersonId` / `onSelect` | .4 |
| `graph.highlight_persons` | `person_ids[]` | **无** | 新增视觉高亮 | .4（可延后） |
| `open.event_card` / `open.person_card` | `event_id` / `person_id` | 时间轴有卡片、图谱有面板，形态不统一 | 需抽象抽屉组件（SPEC §3.1 本就要求） | .4–.5 |
| `ask.suggest` | `questions[]` | 无 | 追问 chips | .6 |
| `none` | — | — | — | — |

**动作信封统一字段**：`id`（幂等键，同一次 `request_id` 内只执行一次）、`type`、`payload`、`target`（`surface: "timeline" | "graph" | "ask"`，供前端判定同页/跨页）、`auto`（**仅建议值**，默认 `false`；Q2 下由前端按路由强制覆盖）、`label`（按钮文案）、`reason`（可选，用于埋点/调试）。

**执行规则（前端）**：

1. 只执行能力白名单内的类型；未知类型 → 忽略 + 上报 `unsupported_action`。
2. 执行前用本地数据校验 ID 存在；不存在 → 不白屏，提示"数据版本不一致，请刷新"。
3. 按数组顺序执行；同一 `request_id` 后到的动作覆盖先到的（以最后一次意图为准）。
4. **不信任后端 `auto`（Q2）**：前端按 `target.surface === 当前路由` 判定——同页自动执行；跨页（含 `/timeline` → `/graph`、`/ask` → 任一模块）一律渲染为确认按钮，用户点击后才跳转并执行。
5. 每个动作执行后记录埋点（type / 成功 / 耗时），用于 V1.0.7 的评测。

> Q5 的候选选择**不属于** `ui_actions`，走独立 `clarification` 分支；前端渲染候选列表，用户选择后重新请求，避免"澄清"被当成一次可撤销的页面动作。

### 5.5 为什么不让后端直接返回"完整视图状态"

常见做法是后端直接返回 `{"route":"/timeline","query":{"mode":"detail","dynasty":"秦","event":"qin-unify"}}`。本项目**不建议**，原因：

- "秦汉图只收东汉 ≤184、三国图收 ≥188"（`person-graph.ts:215-216`）这类业务规则**已经写在前端数据层**，SPEC §7.15 明确要求"集中在数据层，不得散落"。后端若复制一套，必然漂移。
- 简阅模式只显示 `importance=3`、模式切换有记忆（`lastDynastyByGroup`），这些是纯视图规则，后端不应知道。
- 分期映射 `ERA_TO_SCOPE` / `SCOPE_TO_ERA` 也是前端数据。

**推荐分工**：

- 服务端：回答 + 引用 + 实体 ID + 语义动作（"聚焦这个事件/这个人"）。
- 快照导出时**预计算** `person.era_ids`、`event.era_ids`、`era.members`（由前端数据模块生成，保证与渲染同源），让后端无需重算也能给出 `era_id`。
- 前端：`resolveAction(action) → 页面状态`，用本地数据完成 mode/dynasty/era 推导。
- 同时保留一个可选字段 `deep_link`（如 `/timeline?event=qin-unify`），用于分享与降级（前端解析失败时也能跳转）。

### 5.6 Action 落地的前端改造（最小集）

| 改造 | 原因 | 工作量级别 |
|---|---|---|
| 时间轴/图谱页面状态从 URL 派生（`useSearchParams` + `router.replace`） | 深链接、刷新恢复、Action 可复用 | 中 |
| AppShell + Agent 容器（Q1 已定：全局抽屉 + `/ask` 共用会话） | 决定"同页自动/跨页确认"的边界（Q2） | 中 |
| `ActionBus`（Context 或轻量 store） | 页面状态与动作解耦；避免 prop drilling | 小 |
| `PersonGraph2D` 增加受控选中/高亮 props | 目前无法外部打开两人关系面板 | 中 |
| 时间轴增加"高亮集合"（可选） | "高亮时间轴"若包含多事件/区间 | 中 |
| 统一实体卡片/抽屉 | SPEC §3.1 要求；目前无 | 中–大 |

**关键提醒**：UI Action 的"联动"不等于"让 Agent 直接操作 DOM"。必须走"动作 → 页面状态 → React 渲染"的单向流；D3 子树的命令式渲染（`PersonGraph2D` 内部 `svg.selectAll`）只接受数据驱动的 props，不接受外部 DOM 命令。

### 5.7 错误与降级（建议写进 API 契约）

| 场景 | 行为 |
|---|---|
| 模型超时/网关 5xx | 返回 `ok:false` + `retryable:true`，前端显示"已使用本地摘要"（若抽取式可用） |
| 工具无结果 / 无依据（Q4） | `answer.mode = "insufficient"`，固定「资料不足」文案 + ≤3 条相关条目（明确标注"不是答案"），**不进入生成环节**；`ui_actions` 只给"浏览时间轴/关系图"兜底 |
| 实体歧义（Q5） | 有上下文（朝代/分期/当前中心）→ 自动收敛到唯一候选；无上下文 → `clarification` 返回候选（2–3 个，带消歧副标题）；前端不得默认选第一条 |
| ID 不存在/版本不一致 | 前端忽略动作 + 提示；后端在 `trace` 里记录 |
| 超范围问题 | 固定拒答（沿用 SPEC §8.8），`answer.mode = "refusal"` |
| 提示词注入 | 工具只读 + 动作白名单 + 最大工具轮数（如 4）+ 最大 token；不执行用户提供的 URL/代码 |
| 许可（Q6） | 非商用；回答/引用/页脚/API `attribution` 均带来源与 CC BY-NC-SA 声明；商用前必须替换 shiji-kb 派生数据 |

### 5.8 OneAPI / XiaoHong-v1 接入注意

这是唯一一个**无法从仓库验证**的外部依赖。V1.0.1 必须做一个"能力验证 spike"（一天量级），确认：

1. 是否 OpenAI 兼容（`/v1/chat/completions`）、是否支持 `response_format=json_object`、是否支持 function/tool calling；
2. 上下文窗口与中文长文稳定性（回答 150–400 字 + 8 条检索片段）；
3. 超时/并发/限流/计费；是否有 `stream`；
4. 确定性（同 prompt 多次输出是否稳定，影响评测）；
5. 数据合规：问题与历史数据是否会离开本机、是否可关闭日志。

**设计上的防御**：无论模型是否支持 tool calling，服务端都按"**结构化意图 → 规则工具计划 → 模型仅在候选内选参 → 服务端校验**"实现。模型不支持 tool calling 时，退化为"单次 JSON 意图抽取 + 规则执行"，V1.0 仍可交付。

另：SPEC §10 目前写"LLM key 存本地、问答直连 provider"，与"通过 OneAPI 网关由后端统一调用"冲突，需在 V1.0.1 一并修订 SPEC。
