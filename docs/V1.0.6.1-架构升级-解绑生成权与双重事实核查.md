# V1.0.6.1 架构升级：解绑生成权与引入双重事实核查

> 版本：V1.0.6.1（2026-11-25）
> 定位：在 V1.0.6「多轮记忆 + 会话持久化」底座上，完成 **回答正文（markdown）生成权从服务端解绑给模型**
> 与 **双重事实核查（FactCheck）** 的架构升级。
> 前置版本：[V1.0.6 多轮记忆与会话管理](../CHANGELOG.md)；本版不新增数据、不改时间轴 / 图谱视图。

---

## 1. 背景与问题

V1.0.6 的问答链路仍然是「服务端写死正文」：

- 模型只负责选 evidence / citation，`FinalAnswer.markdown` 由 `EvidenceValidator` 用工具原文
  拼装成 `[人物关系图]` / `[时间轴·大事记]` 两节事实罗列；
- 回答**没有深度总结**（没有「史令分析」），对比类问题只能额外触发一次 V1.0.5.4「二次归纳」，
  两条正文分字段下发，体验割裂；
- 模型协议里甚至没有 `markdown` 字段（Prompt 明确写「正文由服务端写死」），模型无法组织语言、
  无法按用户身份（科普 / 考点 / 爱好者 / 考据）调整深度。

V1.0.6.1 的目标：**正文交给模型写，但幻觉由服务端两道核查兜住**——既能写出有深度、有风格的
「史料实证 + 史令分析」，又保证正文里的年份 / 人物 / 书名 / 引文都能在本轮工具结果中核验。

## 2. 四步重构清单

> 需求原文给出「步骤一」的完整 Few-Shot 源码；步骤二~四按同一架构目标实现，
> 并在本文档中固化验收口径。

### 步骤一：`backend/agent/prompts.py` 注入 CoT 与 Few-Shot

1. **废除**旧对比归纳 Prompt：删除 `COMPARISON_SYNTHESIS_SYSTEM_PROMPT`、
   `build_comparison_synthesis_messages`（V1.0.5.4 二次归纳层随之从 Orchestrator 移除）。
2. **`_SYSTEM_TAIL` 重写**：
   - 删除「正文由服务端写死 / 不存在 markdown 字段 / 你无法决定任何用户可见文本」等旧描述；
   - 明确 grounded 必须在 `answer.markdown` 输出两节正文：
     `### 📜 史料实证`（只写可核验事实）+ `### 💡 史令分析`（归纳 / 因果 / 对比 / 辩证）；
   - 新增【思维链（CoT）】约束：每一步 `thought` 先想清楚用户是谁、证据够不够、下一步查什么；
     final 的 `thought` 必须完成「事实 → 关系 → 推断」的归纳；
   - 新增【双重事实核查】约束：年份 / 人物 / 书名 / 引文 / 量化史实的白名单要求与退回重写规则。
3. **追加 `_FEW_SHOT_PROMPT`**：需求原文的五类优秀示例（大白话科普 / 基础考点 / 影视剧纠偏 /
   对比分析 / 史料考据与辩证）逐字保留，包含 JSON 示例里 `\n` 转义符，固定追加在
   System Prompt 最末尾。

### 步骤二：`backend/agent/schemas.py` 解绑 markdown 生成权

- `ModelAnswer` 恢复 `markdown: str | None`（≤10000 字符）：grounded 的模型正文进入协议；
- `FinalAnswer.markdown` 语义改为「模型正文通过双重核查后采用；否则回退服务端事实实证正文」；
- `comparison_analysis`（V1.0.5.4 遗留可选字段）保留契约兼容，但**新回答恒为 None**；
- `AgentResult.fact_check` 新增内部观测字段，映射到 API `trace.fact_check`。

### 步骤三：新增 `backend/agent/factcheck.py`（第二重文本级核查）并接入 Orchestrator

**双重事实核查 = 两道彼此独立的核查：**

| 层级 | 实现 | 检查内容 | 失败处理 |
|---|---|---|---|
| 第一重 · 证据级 | `agent/validator.py::EvidenceValidator`（既有） | evidence / citation 是否来自工具真实返回、类型一致、有详情、fact_usable、citation 与 evidence 同源、双源覆盖 | 强制降级 `insufficient` |
| 第二重 · 文本级 | `agent/factcheck.py`（本版新增） | `markdown` 的两节结构 / 长度 / 年份 / 人物 / 书名 / 引文逐字可核验；量化数字非阻断 warning | 退回重写（≤2 次）→ 仍失败则回退服务端事实实证正文 |

FactCheck 的确定性规则（全部来自本轮工具真实返回，不调用模型）：

1. **年份**：正文中每个「必须校验」的年份必须出现在工具结果年份集合中，
   `前221年` / `公元前221年` / `221年` 按绝对值视为同一纪年；
2. **人物**：正文中出现的已知历史人物名（快照人名 / 别名词典正向匹配）必须在本轮工具结果
   （人物详情 / 事件描述 / 参与者 / 史料文本）中出现过；单字名跳过，避免「开启」误判「启」；
3. **书名**：正文中《…》必须来自工具结果的书目 / 史料出处 / 史料原文；
4. **引文**：长度 ≥8（去标点）的中文直接引文必须能在工具结果文本中逐字找到（忽略空白 / 标点差异）；
5. **结构**：grounded 正文必须同时包含「史料实证」「史令分析」两节；
6. **量化史实**：数字 + 量词（万 / 吨 / 石 / 件 / 里…）不在工具语料中时记 warning，
   提示词要求估算必须带「约 / 估计」等限定词。

Orchestrator 的采用策略（`AgentOrchestrator._decide_markdown`）：

```
final(grounded)
  ├─ 模型没写 markdown → 服务端事实实证正文（status=server_fallback，兼容旧协议/离线脚本）
  ├─ FactCheck 通过   → answer.markdown = 模型正文（status=passed）
  ├─ FactCheck 不通过 → 问题清单发回模型重写（最多 MAX_FACT_CHECK_REPAIRS=2 次）
  └─ 重写仍不通过     → 服务端事实实证正文（status=fallback，downgraded=True）
```

> 安全不变量：**未经文本级核查的模型文本永不展示给用户**；回退路径只用工具原文。

## 3. 关键设计决策

### 3.1 为什么保留服务端「事实实证」正文？

模型正文要经过两重核查才能上屏；一旦模型连续写不出可核验正文（或旧协议 / 离线脚本不写
`markdown`），服务端必须有一条**确定不产生幻觉**的兜底路径——即 V1.0.6 的「工具原文事实罗列」。
该路径同时保证：老测试、离线评测、模型抽风时回答质量不倒退。

### 3.2 为什么不做「模型自我核查」的第三次 LLM 调用？

- 成本与延迟不可控（一次问答可能变成 3 次模型调用）；
- LLM 自检无法给出确定性判据，反而引入新的幻觉面；
- 年份 / 人物 / 书名 / 引文都能用确定性规则核验，规则失败时的修复轮本身就是模型重写。

### 3.3 为什么提升 `LLMClient.MAX_CHAT_MESSAGE_CHARS`？

System Prompt 增加完整 Few-Shot 后实测 **23.3k 字符**（旧上限 20000 → 真实问答会直接 503）。
V1.0.6.1 将单条消息上限提升到 32000 并保留有界校验；`test_agent_markdown` 增加
「System Prompt < 单条消息上限」回归断言，防止后续 Prompt 膨胀再次打爆真实链路。

### 3.4 对比分析（V1.0.5.4）如何退役？

「💡 史令分析」现在由模型写在 `markdown` 里，且必须通过 FactCheck；原「二次归纳」独立调用
（`_attach_comparison_analysis` / `_request_comparison_analysis`）整体删除。
`agent/comparison.py` 的**事实块构建 / 年份人物白名单 / A-B 主体识别 / 兜底实体收集**纯函数保留，
被 `agent.factcheck` 复用；对比类「图谱兜底」链路保留（模型 insufficient 但 A/B 实体已在手时，
仍由服务端给出 grounded 事实实证正文，`trace.fact_check.status=server_fallback`）。

### 4.3 真实 LLM 验收（ModelScope `Qwen/Qwen3.5-35B-A3B`）

验收问题（覆盖 Few-Shot 五类画像）：

1. 古代人打仗，动不动就几十万大军，他们平时得吃多少粮食啊？粮草运输真的有那么难吗？
2. 秦始皇为什么被称为「千古一帝」？他到底做了哪些最重要的贡献？
3. 三国时期的周瑜，真的像《三国演义》里写的那样心胸狭窄吗？真实历史中他跟诸葛亮到底熟不熟？
4. 商鞅变法与王安石变法的区别，在背景和核心目的上有什么本质不同？
5. 关于西汉海昏侯刘贺被废的真实原因，到底是其品行不端，还是霍光集团的政治清洗？

通过标准：`mode=grounded`；`answer.markdown` 含「史料实证 + 史令分析」两节；
`trace.fact_check.status=passed`（或明确回退原因）；回答无工具结果外年份 / 人物 / 书名 / 引文。

**实测结果（2026-11-25）：**

| 问题 | 结果 | 说明 |
|---|---|---|
| q1 粮草后勤 | `grounded` / `fact_check=passed` | 两节齐备；官渡之战事件 + 史料引用；数字估算带限定词 |
| q2 秦始皇贡献 | `grounded` / `fact_check=passed` | 两节 + `[时间轴·大事记]` / `[人物关系图]` 来源标注 + 正史引文（RAG 原文） |
| q3 周瑜/诸葛亮 | 首轮 `insufficient` → 提示词补强后 `grounded` / `passed` | 首轮模型未检索正史、关系库无定性记录即判资料不足；补强「影视剧纠偏类必须补 `search_historical_text`」与「关系库无定性记录 ≠ 无法回答」后，复测以赤壁之战正史记载 + 人物主数据 grounded |
| q4 商鞅 vs 王安石 | `grounded` / `fact_check=passed` | 「破而后立 vs 补而不破」两节对比分析，年份可核验 |
| q5 海昏侯刘贺 | `grounded` / `fact_check=passed` | 官方叙事 / 权力博弈 / 辩证结论；书目《汉书·霍光传》可核验 |

> **结论**：五类画像问题均已逐题通过「模型生成 + 双重核查」验收。
> 随后继续复跑时上游模型账号额度耗尽（`429 insufficient balance`），失败请求按既有约定返回
> 502 envelope；这属于模型账号配额问题，不是本版代码缺陷。

**环境遗留（非本版代码问题）**：`backend/.env` 的备用模型 `Qwen/Qwen3.5-8B-Instruct` 在当前
ModelScope 账号不可用（`Invalid model id`）；主模型限流时自动降级会 502。建议后续把
`MODELSCOPE_FALLBACK_MODEL` 改为账号可用模型（如 `Qwen/Qwen3.8-Flash-Next`）并补一次降级验收。

## 5. 风险与后续

- **上下文预算**：System Prompt 23.3k 字符 + 工具结果消息 → 长回合的 token 成本上升；
  V1.1 可考虑把 Few-Shot 按问题类型动态注入（当前固定全量注入以保证风格稳定）。
- **核查严格度**：书名 / 引文逐字校验会拒绝模型的合理转述（例如把《三国志·周瑜传》写成
  《周瑜传》），修复轮会引导模型改用工具返回的原文；若线上发现误杀率偏高，
  可在 `factcheck.MIN_QUOTE_CHARS` / `_book_allowed` 上做白名单放宽（需补回归用例）。
- **量化 warning**：目前不阻断，只进 `trace.fact_check.warnings`；V1.1 可结合评测统计决定是否升级为阻断。
- **Ruff 全量格式化**：本版新增文件已通过 ruff check；存量文件的 `ruff format` 仍按
  [V1.0.7-TODO.md](V1.0.7-TODO.md) 计划执行，不混入本版 diff。
